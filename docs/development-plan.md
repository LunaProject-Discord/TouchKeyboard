# 開発フェーズと受け入れ基準

各フェーズの動作確認は開発者が実機で行う。Claude Code はビルドが通った時点で停止し、動作確認を依頼すること。

フェーズをまたいで先に進まない。とくに Phase 1 は設計の正しさを決める分岐点であり、ここが通らないまま積み上げると原因の切り分けができなくなる。

## Phase 0 — 基盤

プロジェクト雛形と P/Invoke ラッパー。

- `SendInput` の宣言とラッパー
- `SetWindowLong` / `GetWindowLong` による拡張スタイル適用
- `SHAppBarMessage` の宣言と `APPBARDATA` 構造体

相互に独立しているため並列実装可。

**受け入れ基準**: ビルドが通る。

## Phase 1 — 最小の入力（最重要）

A / Space / BackSpace の 3 キーのみを持つウィンドウ。見た目は問わない。

**受け入れ基準**:

1. メモ帳にフォーカスを保ったまま文字が入力される
2. ATOK をオンにして打鍵したとき、通常のキーボードと同じく変換候補が出る
3. **意図的に打ち間違えたとき、ATOK の補正が働く**

3 が満たされなければ以降に進まない。原因は次のいずれかである可能性が高い。

- `KEYEVENTF_SCANCODE` を指定していない
- `SendInput` の構造体レイアウトの誤り（`MOUSEINPUT` とのユニオンサイズ、64bit のパディング）
- `cbSize` に渡す値の誤り

## Phase 2 — フルレイアウト

外部定義からの読み込み、修飾キーのラッチ、Fn 段、拡張キー対応。

**受け入れ基準**:

- JIS 配列の全キーが正しく入力される
- Ctrl+C / Ctrl+V が動作する
- Shift+英字で大文字が入る
- 矢印キーでカーソルが移動する
- 半角/全角キーで IME がオン・オフする
- 修飾キーのラッチとロックが視覚的に区別でき、期待どおり解除される

## Phase 3 — ドッキングと DPI

AppBar 登録、高さ変更、設定の永続化、Per-Monitor DPI 対応、タスクトレイ常駐。

**受け入れ基準**:

- 最大化したウィンドウがキーボードに隠れない — **合格**
- 高さを変更すると他アプリの作業領域が追従する — **合格**
- モニタ間移動・スケーリング変更でレイアウトが破綻しない — **スケーリングのみ合格**
- 再起動後に高さと表示状態が復元される — **合格**
- アプリ終了時に `ABM_REMOVE` が呼ばれ、作業領域が元に戻る — **合格**
- 二重起動せず、2 回目の起動が既存ウィンドウの表示になる — **合格**（追加）

### スケーリング変更の実測

150% と 200% で、確保領域が `HeightDip × 倍率` と完全に一致した（差 0 px）。

```
200%: reserved 1020 px = キーボード 462×2 (924) + タスクバー 48×2 (96)
150%: reserved  765 px = キーボード 462×1.5 (693) + タスクバー 48×1.5 (72)
```

高さを DIP で保持している設計が意図どおり働いており、倍率を変えてもキーボードの見かけの大きさが変わらない。

**測定時の注意**: PowerShell など DPI 非対応プロセスから測ると、Windows に仮想化された座標が返り実際と食い違う。`SetProcessDpiAwarenessContext` で PMv2 を宣言してから測ること。

### 未検証

**モニタ間移動。** 外部ディスプレイが無いため確認できていない。接続時に以下を確認する。

- ドッキング先モニタをトレイメニューから選択できるか
- モニタ構成変更後に復帰できるか（`MonitorInfo.Resolve` のフォールバック）
- 異なる DPI のモニタ間で高さが物理的に破綻しないか

### 追加した機能: タスクバーを覆う配置

標準タッチキーボードはタスクバーを覆って画面下端まで伸びる。これに合わせる選択肢を設けた（トレイメニュー「タスクバーを覆う」、既定はオン）。

**AppBar が確保する領域は変えない。** 確保はタスクバーの上で行い、ウィンドウだけを画面下端まで伸ばす。作業領域の計算に影響しないため、他アプリの配置は従来どおり。タスクバーも最前面ウィンドウなので、`SetWindowPos` の挿入位置に `HWND_TOPMOST` を明示する必要がある。

**注意**: 覆っている間は通知領域に触れない。ドッキング中はヘッダーを畳んでいるため画面上の ✕ も無く、**トレイが唯一の操作経路**になる。設定変更や終了を行うには、いったんキーボードを隠す（グリップを下へ払う）か、「タスクバーを覆う」をオフにする。

当初は画面下端からのスワイプでタスクバーが現れてしまい、標準タッチキーボードとの違いになっていた。原因はシェルが管理する Z 順に入れていなかったこと。`uiAccess` の対応（`requirements.md` 9 章）で上位のバンドに入ったため解消した。

#### 実装上の注意（ちらつきと寸法の一致）

いずれも「AppBar の確定した矩形」と「実際に描くウィンドウの矩形」が別物であることに起因する。

- **位置決めは 1 回にまとめる。** `ABM_SETPOS` 後にウィンドウを動かし、その後さらに下端まで伸ばすと、途中の「タスクバーの上に置かれた状態」が見えてちらつく
- **表示はドッキングの後に行う。** `Show()` を先にすると位置が確定する前に描画される。非表示のウィンドウでも `SetWindowPos` は効く
- **ドラッグ中も他の AppBar が占める量を差し引く。** `ABM_QUERYPOS` はタスクバーを避けて上端を押し上げるため、これを省くと指を離した瞬間にタスクバーぶん高さが跳ねる

### この段階で見つかった不具合

いずれも数値やログで確認しないと気付けないものだった。WPF 版での事象だが、1 と 3 の対処は WinUI 3 版にも引き継いでいる。

1. **終了時に `Environment.Exit` がハングし、スレッド 1 本のゾンビが残る** — 後片付け（`ABM_REMOVE`・設定保存・トレイアイコン削除・Mutex 解放）は全て完了していたため、作業領域は正常に戻っており表面化しにくかった。`Process.Kill` で即座に落とすことで解消。ハングの根本原因は未特定
2. **ゾンビが Mutex を解放するため二重起動の抑止が破れる** — 1 の副作用
3. **`HWND_BROADCAST` が既存インスタンスに届かない** — `ShowInTaskbar="False"` により WPF が不可視の親ウィンドウを作り、ウィンドウが「所有された」状態になるとブロードキャストの配送対象から外れる。名前付きイベントによる通知に変更して解消

## Phase 3.5 — WinUI 3 への移行と外観の調整

Acrylic が `WS_EX_NOACTIVATE` のウィンドウで効かないため WinUI 3 へ移行し、そのうえで外観と操作性を実機に合わせて詰めた。移行の判断は `requirements.md` 8 章、検証結果は `technical-notes.md` を参照。

- 7 段構成（半分の高さのファンクション段、Delete、逆 T 字の矢印クラスタ）
- BS / Tab / Shift / Win / Enter / 矢印を Fluent アイコン化し、語として意味を持つものは文字を併記
- L 字の Enter（上下 2 段を 1 つのキーとして結合）
- キー幅の再配分（左端を太く、右端を細く）
- 修飾キーの押さえ続け（マルチタッチ）
- ドッキング中はヘッダーを畳む
- 通知領域メニューをタッチのタップ位置に出す

**受け入れ基準**: 見た目の一致度と打ちやすさは開発者が実機で判断する。

### 実機で確認済み

- 文字入力と ATOK の入力ミス補正（絶対制約 1 が WinUI 3 でも成立）
- 非アクティブのまま Acrylic が効くこと
- 修飾キーのラッチ・ロック・押さえ続け、複数キーの同時押し
- 長押しリピート
- 高さのドラッグ
- トレイの「表示 / 非表示」とモニタ選択、メニューがタッチのタップ位置に出ること
- トレイからの終了。作業領域が戻り、ゾンビも残らない（下記）
- 「タスクバーを覆う」

終了後の実測値。予約が完全に解除されていることを数値で確認した。

```
PROCESS : なし
SCREEN  : 2880x1920
WORKAREA: (0,0)-(2880,1824)      下に残るのは 96px = タスクバーのみ
```

### 未検証のまま残っているもの

- トレイメニューの「Windows 起動時に開始」
- トレイメニューの「自動表示」（Phase 4 が未実装のため、現状は設定の保存のみ）
- モニタ間の移動（外部ディスプレイが無いため）

## Phase 4 — 自動表示

UI Automation の `FocusChangedEvent` 購読と、`ControlType.Edit` / `TextPattern` による判定。

**受け入れ基準**:

- メモ帳、ブラウザのアドレスバーとテキストフィールド、エクスプローラの検索欄で自動表示される
- 入力欄から外れると自動的に隠れる
- 自動表示のオン／オフが機能する

取りこぼしは前提であり、実使用しながら個別に対応する。ここで完璧を目指さない。

### 実装した内容

`Automation/FocusWatcher.cs`。判定は `ControlType.Edit` / `Document` に加えて、キーボード入力可能かつ `TextPattern` に対応するものを拾う。編集可能な ComboBox は `ValuePattern` で判定し、いずれも `ValuePattern.IsReadOnly` で読み取り専用を除外する。

- 隠す判断は 400ms 遅らせる。表示は即時
- 自動での開閉は設定に保存しない（`ShowKeyboard(remember: false)`）。設定は利用者が選んだ状態を表すものにする
- 既に表示中の表示要求と、既に非表示の非表示要求は空振りさせる。AppBar を余計に登録し直さないため

**代償**: `System.Windows.Automation` は WPF と同じフレームワークに含まれるため、`FrameworkReference` を足すと自己完結出力が 238MB → 303MB になる。`UseWPF` は使っていない（WPF の XAML ビルドが WinUI のコンパイラと衝突するため）。サイズを戻すには UI Automation の COM API を直接扱う必要がある。

### 実使用で見つかった問題と対処

いずれも計測して原因を特定してから直した。推測で条件を足していない。

**1. ブラウザで閲覧中つねに表示される**

Edge の Web ページは、メモ帳の編集領域と同じ `ControlType.Document` でテキストパターンにも対応する。両者を分けているのは `ValuePattern.IsReadOnly` だけだった。読み取り専用の判定を種別より先に置いて解決。

| | メモ帳の編集領域 | Edge のアドレスバー | Edge の Web ページ |
|---|---|---|---|
| 種別 | Document | Edit | Document |
| textPattern | True | True | True |
| **isReadOnly** | **False** | **False** | **True** |

**2. サジェストが出ると消える**

アドレスバーへの入力中に、フォーカスが読み取り専用の Document へ移る。当初は猶予時間を延ばして凌ごうとしたが、これは Edge の挙動に合わせた対症療法だった。

前面ウィンドウを調べたところ、サジェストは**メインウィンドウに所有された `WS_POPUP`** だった。所有関係は Win32 が補助 UI を表すために持つ仕組みなので、これで判別できる。

```
SHOW  fg=0x103B0   owner=0x0        CAPTION   ← アドレスバー
----  fg=0x39125A  owner=0x103B0    POPUP     ← サジェスト
```

なお、キャレットの有無（`GetGUIThreadInfo`）と要素のウィンドウハンドルも試したが、どちらも使えなかった。Chromium は Win32 のキャレットを作らず、要素のハンドルは常に 0 を返す。

**3. 物理キーボードがあるときは出さない**

`SM_CONVERTIBLESLATEMODE` で判断する。Windows 自身がタッチキーボードの自動表示を決めるのに使う値。Raw Input でキーボードを数える方法は採れない（実機では仮想デバイスを含め 8 個が並ぶ）。

- 装着されたら隠す（`WM_SETTINGCHANGE` の `ConvertibleSlateMode`）
- 外されたら、フォーカスを調べ直して入力欄なら出す。**外しただけではフォーカスが動かない**ため、自分から確かめ直す必要がある
- 物理キーボードで打たれたら隠す。低レベルフックには自分が `SendInput` で送ったキーも流れてくるので、`LLKHF_INJECTED` が立っていないものだけを物理入力とみなす

限界: `SM_CONVERTIBLESLATEMODE` が表すのは変換型デバイス自身の姿勢だけで、後から繋いだ Bluetooth / USB キーボードは反映されない。ただし打鍵されれば隠れる。
